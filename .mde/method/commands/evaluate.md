# mde evaluate

Purpose: derive the plan's **real candidate artifacts** — the actual specs, entity
files, diagrams, page specs (the durable outputs the loaded targets define) — and
record every one in the plan manifest, so the user reviews the **real files** before
`go` accepts them. **Required before `go`** — `go` will run `evaluate` automatically
if skipped, then proceed straight into accepting the produced artifacts in the same
invocation (no separate confirmation step).

The candidate artifacts **are the review surface** — there are no separate summary or
digest files. Evaluate generates the real files and records each in the manifest
(`output.manifest`) as a plan-owned entry; the user reviews and edits those files
directly. `go` accepts the manifest-listed set; `cancel` rolls back only that set.
See `plan-status` §7.1 Manifest & ownership boundary (reference).

## Behavior

**Ordered, observable steps — `tasks.md` is the step ledger, written first.** Evaluate's steps
run **in order** and each step is **observable**: before doing anything else, **write `tasks.md`
from the tasks template** (the stage list, all unchecked) so the ledger of where evaluate is
*always exists*. Then, as each step completes, **tick its `tasks.md` line and checkpoint it in
`status.md`/`log.md`** (e.g. "step 5: manifest planned — N entries"). At any pause, the plan's
`tasks.md` + `status.md` say exactly which step is done and which is next — evaluate is never a
black box between `start` and `evaluated`. A running evaluate with **no `tasks.md`** means the
step ledger was never created — the agent went off-script; that is itself an evaluate defect.

**Steps are gated on their predecessors — do not skip ahead.** In particular, the ordering below
is a contract, not a suggestion:
- **Gate 1 (target inclusion)** runs on `impact.md`'s loaded targets alone — it needs **no**
  manifest, so it runs *before* the manifest is planned. **This gate is EXECUTED, not eyeballed:**
  run `node .mde/verification/verificationRunner.mjs . <plan-dir> --gate=1` and capture its output
  to `plans/<plan-id>/evidence/logs/verify.log`. It exits **0** when every required target
  (transitive `requires` ∩ tech-stack) is loaded or excused, **non-zero** with a `[FAIL]` naming
  each missing target. Do **not** tick step 4 or proceed while it exits non-zero — a required target
  neither loaded nor excused **stops evaluate here**. Fix the target set (load it) or record the
  exclusion in `scope.md ## Excluded targets` with a reason, then re-run the gate until it exits 0.
  Ticking step 4 without a clean gate run (exit 0 in `verify.log`) is a rubber-stamp — the defect
  this step exists to prevent.
- **Planning the manifest** (write `tasks.md` + the `planned` `output.manifest`) happens **before
  any artifact is generated**. The planned manifest is the ownership boundary.
- **Generation must not begin until the planned manifest exists.** Writing a source/migration/test
  file with **no `output.manifest`** present is a hard violation of the sequence — the file is
  unowned (cancel/change cannot roll it back) and invisible to verification (which reasons from the
  manifest). If you reach the generation step and no planned manifest exists, **STOP**: do not
  generate; report that manifest-planning was skipped and go back and do it first. Do not
  reverse-engineer a manifest from files already on disk (that launders unplanned output into
  looking planned, and is the filesystem-inference anti-pattern) — plan the manifest from the
  loaded targets + specs, then generate against it.

1. Confirm scope, operation, assumptions, and exclusions from the draft conversation. **Take the plan's scope as given — large scope is valid and `go` builds it in one pass.** Do not declare the scope "too big," do not ask the user to narrow it, and do not recommend splitting into smaller plans on the basis of size or effort; splitting is the user's choice for a real reason (release timing, dependency ordering, explicit phasing), never an agent-imposed precondition. Clarify only genuine **ambiguity** (what is in/out), not breadth.

1a. **Handle every change to the plan as intent — capture it and carry it through.** Any change the user makes to the plan, however it reaches you — a chat request, an edit to a candidate artifact, a plan file (scope), reviewer feedback — is a commitment, not a suggestion. Find each change wherever it is, understand *what the user meant*, and apply that intent through the plan and everything it produces: record it as a resolved `discussion.md` decision, re-derive **all** the dependent artifacts (the candidate artifacts, `impact.md`, `output.manifest`, `tasks.md`) so none of them disagrees with it, and confirm to the user that it is captured and will be built. A change that landed in one artifact but not the others — a page spec renamed a capability but the manifest still names the old one — means the intent was not carried through; that is an evaluate defect. Do not stamp `evaluated` while any change is uncaptured or any artifact disagrees.

   **Evaluation is fully re-deriving — including when only the method changed.** Every `mde evaluate` run regenerates **all** candidate artifacts from the current contract and method, not just the ones a user edit obviously touched, and updates the manifest to match (never silently broadening ownership). If the fingerprint went stale because `.mde/method/` changed (e.g. after `init-app`), the artifacts may now be wrong even though no user input changed — **regenerate them, do not leave the prior run's output in place.** A user's edit to a manifest-listed candidate artifact is preserved as their intent (step 1a); a non-manifest dirty file is external/user-owned and left untouched.
2. **Select the applicable targets** (this is where target loading happens — `go` consumes the result, it does not re-derive). Build the target set as a **union** of two sources, and record it in `impact.md`:
   - **Declarative floor — `applies_when` match.** Load **every** target whose `applies_when` matches the plan's impact (operation type + scope). Do not name targets in this command — iterate the available target profiles and match each one's own `applies_when`. This floor guarantees the obvious targets are never missed.
   - **AI judgment — may add only.** On top of the floor, **add** any target your reading of the plan finds applicable that the mechanical `applies_when` did not catch (e.g. an integration described in prose without an obvious file trigger). The AI may **add** targets; it may **not** suppress an `applies_when` match. Record the final union as one flat list (no provenance distinction).
   - **Close the dependency graph.** After the union, pull in every target the loaded targets `requires:` (transitively) — a target's dependencies are part of loading it, so cross-cutting targets enter here from the `requires:` declarations, not from any rule naming targets in this command. A required target the plan genuinely excludes is declared under `scope.md` `## Excluded targets` with a reason (the inclusion gate checks this).
   - If the plan does design or build work and no stack is recorded, confirm the technology stack (starter stacks in `templates/stack/` plus `custom`) and record it as a resolved `discussion.md` decision entry. **A stack is "recorded" if any of these exist — check them before prompting, and do not re-ask when one is present:** an authoritative `specs/design/tech-stack.md`; a resolved stack decision in this plan's `discussion.md`; **or an initial `specs/design/stack-preference.md`** (written by `init-app` when the user picked a stack at install). When only `stack-preference.md` exists, **adopt its `stackTemplate` as the proposed stack** and carry it into the `discussion.md` decision (confirm rather than re-collect); only fall back to asking when its `stackTemplate` is `later`/absent or the user changes it. Do not prompt for a stack the user already selected at init.
   - For UI work, assign each page a pattern id from `.mde/ui-patterns/ui-patterns.md` (or `custom`).
3. Write or update `impact.md` (plan-local) as the AI-derived commitment record (including the doc plan), and write `acceptance.md` — the derived acceptance criteria + test plan (definition of done) — for the user to confirm. **Requirements** that are business content are written to Business Specs (BA target), not to the plan.
   - **Identify the full impact before listing what you'll produce — `impact.md ## Impact Analysis`.** The `## Artifacts` table is *what this plan produces*; it must be fed by a *complete* identification of *everything the change touches*, so a needed downstream artifact is never silently missed. **Phase 1 (identify):** for **modify/delete**, reverse-traverse the manifest — every existing artifact whose `sourceRef` points at a spec this plan changes or removes is impacted (a changed entity impacts its page, repository, migration, DTOs, tests, docs); for **add**, use judgment — does the change *imply an artifact that does not exist yet* (a new entity → a maintenance page; a new use-case → its own page)? There is nothing to reverse-traverse to for an add, so reason it out. **Phase 2 (disposition):** mark each identified item **this-plan** (it goes into `## Artifacts`) or **deferred** (it goes into `## Deferrals` with a reason + follow-up). Deferral is legitimate; an impacted artifact that is **neither produced nor deferred** is an evaluate defect — the impact was missed. This is the forcing function for the classic gap where a spec change updated the entity but left its page/tests stale and unmentioned.
   - **Derive the acceptance criteria from each loaded target's checks — not from the contract alone.** A loaded target supplies two things: its required *artifacts* (next bullet) **and** its *checks* (the checks its referenced capabilities define), which are the **definition of done** for its scope and become acceptance criteria so `mde go` verifies them and `mde review app` re-checks them. For **each loaded target**, turn its applicable capability checks into acceptance criteria — do not enumerate specific targets or thresholds here; the targets/capabilities are the source of what to cover. A loaded target whose checks are not reflected in `acceptance.md` is an evaluate gap — the same class of defect as a target-required artifact with no manifest entry.
   - **Expand every target-mandated artifact into explicit scope — do not let a doc-materialization task imply it.** For each loaded target, the artifacts it *requires* (not merely suggests) become their own `impact.md` line, `tasks.md` row, and manifest entry. Do **not** enumerate specific artifacts here — the loaded targets and their referenced capabilities are the single source of *which* artifacts are required and *when* (each capability's `## Impact` and `## Checks` carry the trigger and the path); iterate the loaded targets and expand whatever they mandate for the plan's scope. This applies to the diagrams under `docs/diagrams/` (each its own required output, one entry per file) exactly as to specs, source, and tests: a diagram a loaded target's capability mandates for the in-scope work must appear as its own `impact.md` line, `tasks.md` row, and manifest entry, never folded silently into "materialize architecture design." A required artifact with no task and no manifest entry is an evaluate defect.
3a. **Plan the work first — write `tasks.md` and the planned `output.manifest` before generating anything.** (`tasks.md` itself was created as the step ledger at the top of Behavior; here it is filled from the template — it owns the stage order, do not re-sequence it.) Write `output.manifest` as the **planned set**: one entry per artifact the loaded targets mandate, `status: planned`, before any file is generated. This planned manifest is the ownership boundary (see `plan-status` §7.1); it exists *before* the build so a half-finished evaluate still has a plan of what was intended. Checkpoint completion ("manifest planned — N entries") in `status.md`/`log.md`. Then **follow `tasks.md` in order** for the rest of evaluate.

3b. **Generate and verify the candidate artifacts — following `tasks.md` (the cycle the plan's target defines).** **Precondition (hard gate): the planned `output.manifest` from 3a must exist before the first file is written.** If it does not, STOP — do not generate; the sequence was skipped, report it and complete 3a first. Never adopt files already on disk in lieu of a planned manifest. Then, for each planned artifact, **write it to its real project path** and **flip its manifest entry from `planned` to its touch state (`created`/`modified`/`deleted`) the MOMENT that file exists — one item at a time, right after you write it, never batched at the end.** This gives per-item recovery: if evaluate stops or fails partway, the manifest already shows exactly which items are done, so a re-run **regenerates only the entries still `planned`** and **skips any already `created`/`modified`** on disk — it never redoes completed work or reverse-engineers a manifest.

**Produce exactly the outputs the plan's loaded targets mandate — nothing the targets do not.** The targets define what to generate and how to verify it; evaluate does that and no more. A target that outputs specs produces specs; a target that outputs source runs its build/test cycle (install, build, run tests, migrations against a throwaway DB). Do not add outputs a loaded target does not mandate.

An evaluated plan whose mandated output is missing (or, where the target builds, doesn't build or fails its tests) has **failed**; fix it before stamping `evaluated`. A planned entry whose file was never produced is marked `blocked`. Record verification/build/test results in `evidence.md`. **Production logic, not a demo (RULE-CORE-004): the code you generate must get its data from the real database/service/API — NO hardcoded sample records, NO mock or stub returns in production paths, NO silent fallback to fake data when a real call fails (a failure must surface as an error/log, never be hidden behind placeholder data that makes a broken system look healthy), NO no-op controls, NO hand-written coverage/report numbers. Mocks belong in tests, never in shipped code.** If a real dependency genuinely cannot be reached, mark the item `blocked` and record why — do not fake it to look done. **`mde go` does NOT generate or build these — it accepts and commits what evaluate already produced and verified.** This runs on **every** run: a re-evaluation regenerates and re-verifies from the current capabilities and contract (preserving the user's edits per step 1a). The artifacts are the user's to review and edit; there is no separate summary of their *content* (they are the review surface). The one thing status.md **does** summarize is the plain-English **`## Outcome`** — the result + next step — so the user is not left to derive it from the logs.

   **Environment-gated verification — and a capable agent must repair its own toolchain before deferring.** Each capability check declares its `when`: `static` checks run in **every** environment and must never be deferred; `requires-environment` checks (running the test suite, measuring coverage, capturing UI screenshots, applying real migrations) need a runtime/DB/install. Distinguish two cases — they are **not** the same:
   - **Incapable environment (defer is correct).** The agent genuinely has no runtime — e.g. a browser-only agent with no Node/shell, no install, no reachable database. Only then: do **not** mark the check passed and do **not** invent results; record it as **`deferred — requires execution environment`** in `evidence.md` and open a **verification debt** (note in `status.md`/`log.md`: "re-run `mde go` in a capable agent").
   - **Capable agent, broken/missing setup (repair, do not defer).** The agent *has* a real runtime (shell, Node/npm, Python, a package manager) but a check fails because a dependency is missing, an install timed out, a binary is absent, or a service is down. This is **not** "cannot execute" — it is fixable and is part of the job. Remediate within scope (retry/clear-cache/install the specific missing dep, bump the install timeout, start the local service/DB), then run the check. Only if remediation genuinely fails may you defer — recording **what you tried and why it failed**, not just "environment limitation."
   - **No stale-artifact shortcut.** Do not satisfy a check against a **stale build/output** when a fresh one was achievable. `node --check`/compile is **not** a substitute for running tests.
   - **Capture every check's output as an evidence artifact.** Save real stdout/stderr under `plans/<plan-id>/evidence/logs/` and reports under `evidence/reports/`; `evidence.md` references these files rather than restating runs in prose. A check marked `passed` with **no captured artifact** does not satisfy the gate. *Which* evidence artifacts are required is owned by the loaded targets' `## Outputs` (the mandated-output gate) — do not enumerate specific log/report files here; run whatever commands the loaded targets mandate for the plan's scope and capture each one's real output as proof.

   With the environment present, evaluate completes the full cycle and leaves no debt.

3c. **Validate the generated artifacts** per the four-pass model — `tasks.md` carries `7.1`–`7.4` as **four separate checkboxes** (the template owns them); the full model lives in the `capabilities, targets, templates, and validation` reference. **Run and tick each pass individually** — do not collapse them into one "validated" tick.

   **The deterministic passes are EXECUTED, not eyeballed.** After generation, **run the verifier full**: `node .mde/verification/verificationRunner.mjs . <plan-dir> --out=plans/<plan-id>/evidence/logs/verify.log` (no `--gate` — the full run: inclusion + mandated-output + artifact-exists + every capability `check` block). **Use `--out=` so the engine writes `verify.log` as UTF-8** — do **not** shell-redirect (`> verify.log` / `Out-File` write UTF-16 on Windows and corrupt the log). This is the mechanical backbone of **7.1** (planning — every target-mandated artifact is in the manifest; the runner's mandated-output gate) and **7.2** (implementation — every declared artifact exists on disk; the artifact-exists gate), plus the deterministic capability checks that feed **7.4**. The runner exits **0** clean, **non-zero** with grouped `[FAIL]`/`[ASK]` findings. **Pass 7.4 (AI semantic review)** sits *on top* of the executed checks: the AI reads each artifact against its specs/capability intent/template for what a script cannot see, and answers/routes each `[ASK]` in `evidence.md ## Semantic ASK Answers` with concrete artifact/test references. **A pass may be ticked only when the verifier run backing it has no open `[FAIL]`s and every emitted `[ASK]` is answered or routed as a repair-loop finding** — ticking a pass while `verify.log` shows an open `[FAIL]` for it is a rubber-stamp. **7.1 must confirm every target-mandated artifact is in the manifest** — whatever the loaded targets' `## Outputs` mandate for the plan's scope; a mandated artifact with no manifest entry is a planning-pass failure. Any pass that fails is repaired and the verifier re-run before stamping `evaluated`. Do not re-enumerate the passes here — follow the template and the reference.

3d. **Prove the app runs — the runtime gate (applications only).** After the verifier is clean, run `node .mde/method/scripts/verify-app-runtime.mjs . --json plans/<plan-id>/evidence/runtime.json`, appending console output to `plans/<plan-id>/evidence/logs/runtime.log`. This is `tasks.md` stage **7.5** and it is **executable, not narrative**. Every check above this line reads *files*: the manifest, the specs, the traces. All of them pass for an application that does not work — a test suite whose assertions are `readFileSync` + regex stays green with the UI rendering `null`, and a frontend whose fetch failures fall back to hardcoded data renders a convincing screen while reaching no API at all. The runtime gate starts the tiers, exercises every path declared in `openapi.yaml`, drives the real UI in a browser, and fails when the frontend never reaches the API or silently serves fallback data. **A non-zero exit is an evaluate failure like any other** — repair and re-run (stage 8); do not stamp `evaluated`, and do not classify it away at stage 9 on the grounds that the artifacts all exist. "The tests pass" is only evidence when the tests ran the app.

3e. **Substance audit — scoped to THIS plan (a fresh, independent judgment).** After verification and the runtime gate pass, run the audit **on what this plan produced**, not the whole app. Verification (3c) confirms artifacts exist, trace, and conform; the audit asks what a check cannot: are they *genuine* — does the behaviour hold, or does it only look right? This is **not** pass 7.4 (that is the generating session's own semantic review); the audit is performed in a **fresh session** that did not build these artifacts (verification model §3). Steps:
   - **Scope from the plan.** The audit set is exactly the artifacts this plan owns — the `this-plan` rows of `impact.md ## Artifacts` (equivalently, the plan's `output.manifest` entries). Audit **only** the capabilities/entities/use-cases/pages/routes this plan produced or modified; a concern belonging to an untouched capability is out of scope for this plan's audit (that whole-app sweep is `mde review app audit`).
   - **Establish the audit targets — audited vs no-view.** Take the plan's `impact.md ## Loaded Targets`. For each, an audit view exists iff `<METHOD_SOURCE>/targets/audit/<target>.md` is present. Split the loaded targets into **audited** (view exists — you will carry out its `## Audit` blocks) and **not audited (no audit view)** (loaded but no view — nothing examines it). The report MUST declare both lists (see below): a plan can load a target the audit cannot cover, and that gap must be **visible**, not silent — "7 genuine" over a subset reads as whole-plan assurance unless the un-audited targets are named.
   - **Load the relevant audit views** — `<METHOD_SOURCE>/targets/audit/<target>.md` for each **audited** target — and carry out each `## Audit` block against **this plan's** artifacts (drive the running app where the audit needs it; read the specs for BA/design targets).
   - **Report** to `plans/<plan-id>/evidence/audit.md`. Begin with an **`## Audit Targets`** section stating, from the split above: **Audited** (target — audit view) and **Not audited (no audit view)** (target — why: no `## Audit` block ships for it). Then, per concern, a verdict — **genuine | fake | not-exercised** — with the observed witness (server-log line, read-back, the missing operation, the placeholder flow), and which audited target it came from. A `fake` verdict on an in-scope artifact is a finding that goes back to generation (stage 8) like any verification `[FAIL]` — a plan does not stamp `evaluated` with an in-scope artifact its own audit judged fake.
   - This makes the audit runnable **after every plan** (a BA plan audits its capabilities/entities/use-cases; a UI plan audits its pages), scoped to the plan — not deferred to a whole-app review.

4. **Reconcile the manifest** (it was planned at 3a and filled at 3b — this finalizes it, it does not create it). Confirm `output.manifest` follows the schema exactly: the artifact path is the `artifact` field, never a `path` field; required keys `artifact`, `outputType`, `action`, `implementor`, `sourceRef`, `rules`, `mergePolicy`, `status`; optional trace keys `template`, `features`. Every planned entry now resolves to a real file with a final touch state (`created`/`modified`/`deleted`), or is `blocked` where generation failed. A leftover `planned` entry at this point means the work did not complete — do not stamp `evaluated` until it is produced or explicitly `blocked` with a reason. A manifest entry with no real file behind it (and not `blocked`) is an evaluate defect.

   **`sourceRef` is a REFERENCE, not a description — this is mandatory, not best-effort.** Every entry's `sourceRef` MUST be `{ "kind": "<scope-type>", "refs": [ "<real upstream spec file>" ] }`, where `refs` names the **concrete upstream spec instance the artifact serves** — the exact file under `specs/` that this artifact traces back to: the entity spec for a repository/migration/storage-view (`specs/business/entities/<entity>.md`), the page spec for a page (`specs/design/UI/pages/<page>.md`), the use-case spec for a walkthrough, the business-rule spec for a rule test/enforcement, and so on, per the producing target's `## Outputs` **Scope Type** (`perEach`). `kind` is that Scope Type (`entity | use-case | web-page | business-rule | role | business-capability | entity-operation | integration`). A `sourceRef` that is a **prose label, a target name, or a phase word** — `"API"`, `"ARCHITECTURE"`, `"PERSISTENCE"`, `"intent"`, `"BOOTSTRAP"`, `"UI"` — is **INVALID**; it describes, it does not reference. `refs` MUST resolve to real files on disk (at least one). This is what lets verification derive `$item.entity`/`$item.page` and check per-scope coverage by reading along the reference; an artifact whose `sourceRef.refs` do not resolve to a real upstream spec **cannot be traced and is an evaluate defect** — fix it before stamping `evaluated`. (The plan-intent line, e.g. `scope.md#1.1`, is NOT an upstream spec instance; it is where the plan decided to do the work, not what the artifact serves.)
4c. **Final scope self-audit — before stamping `evaluated`, stop and re-examine: "did I finish the ENTIRE scope?"** Do not rely on your memory of what you did — re-read the plan's own `scope.md`, `acceptance.md`, and `output.manifest`, and walk each committed item against what actually exists and passed. For **every** scope item, acceptance criterion, and mandated output: is it *really* done — a real, working, tested artifact — or was it quietly narrowed, stubbed, skipped, deferred, or satisfied by a placeholder (an empty test, a fake/100%-of-nothing coverage report, a vague Gherkin assertion, a "backed by the API" that asserts nothing)? Re-run the executable checks one more time if there is any doubt; a capable runtime that ran anything can run these. This is a deliberate second pass whose job is to catch the *"I dropped part of it"* and *"good enough"* drift — the amount of work is never a reason a scope item is incomplete (see RULE-CORE-001 posture).

   **Re-examine every deferral — the environment is ready for live tests.** Treat this environment as **capable of running live tests** (build, run the suites, coverage, migrations against a real DB). Walk **each** item you marked `deferred` / `requires execution environment` and **re-challenge it**: if it is an executable check and the runtime is present, a deferral is **not** acceptable — **run it now** instead of leaving it deferred. If you *ran any* executable step this session (built, ran a suite, applied a migration), the environment is *proven* capable, so deferring *other* executable checks for "no environment" contradicts your own evidence and is a defect. A deferral survives this audit **only** with captured proof that the runtime is genuinely unavailable *and* remediation was attempted and failed — never as a convenience, a time-saver, or "good enough for now." Convert every unjustified deferral into an actual run before stamping evaluated.

   **A deferral must name a concrete follow-up — and stale ones are closed, not accumulated.** Every deferral this plan records (in `impact.md ## Deferrals` / `scope.md`) must state *why* (a specific cause, not "hygiene"/"good enough"/"recorded in evidence.md" — a reason that points at another file is circular and invalid) and a *concrete follow-up* (the artifact/section to produce and where — a named later plan or condition, not "open if…"). A deferral with no concrete follow-up is skipped work dressed up as deferred (RULE-CORE-001) — either do it now or record a real follow-up. **Cross-plan reconciliation:** also re-examine the **open deferrals of prior plans** (their `pending-actions`/`## Deferrals`): if a prior deferral is now **satisfied** (the deferred artifact/section now exists, was done in a later plan, or became moot because scope changed), **close it** — mark it resolved in that plan's status so `pending-actions` clears; a deferral is not eternal. The open-deferral backlog must reflect *real* outstanding work, not stale items already done elsewhere. (Example: plan A deferred exact panel-action target binding; a later plan B added it — B's evaluate closes A's deferral.) If the audit finds anything short of complete, it is **not** evaluated: fix it, or set lifecycle to `partially-executed`/`blocked` and record the specific gap honestly. Only pass this gate when every scope item is genuinely, verifiably done.
5. Check off the completed `tasks.md` stages, update `log.md` and derived `status.md`; set lifecycle to `evaluated`. **Honest status (RULE-CORE-004):** if any target-required artifact is missing (a manifest-mandated entry with no real file, or an empty/stub stand-in) or could not be generated, **do not** mark the validation stage (6) complete — set lifecycle to `partially-executed`/`blocked` and record the gap. **Never substitute a demo, skeleton, stub, or fake** to make it look done. Status carries two separate, derived flags (never merged): `pending-actions` — `open` if any `discussion.md` entry is `status: open` or `scope.md` has any Deferred item, else `none` (Non-goals never count); and `verification-debt` — `none` at evaluate time (no checks have run yet), it only opens during `mde go` when an executable check is deferred for lack of an environment.
6. Stamp an **evaluation fingerprint** so staleness is detectable. It covers the plan inputs, the method version, **and the base**, so a change to any of them makes the fingerprint stale:
   - plan inputs — a hash of **every user-editable plan input**: `scope` / `discussion` / `impact` / `acceptance` (or the `log.md` event count), plus the manifest-listed candidate artifacts the user reviews and edits. A user edit to a manifest-listed artifact is a plan modification; if the fingerprint ignored it the plan would build stale.
   - **method version** — a hash/marker of the loaded method package (`.mde/method/` — rules, targets, templates; e.g. the method `CHANGELOG.md` version or a content hash of the loaded rule/target/template files).
   - **base** — the branch state the plan's commits sit on (e.g. the merge-base commit with `main`, or the branch tip the plan was evaluated against). A plan is **base-bound**: if the base moves (the branch advanced underneath it) or the plan is taken to a different base (the future `mde move`), the evaluation is invalid and the plan must be re-reviewed + re-evaluated against the new base. This is the forcing function for changing a plan's base — there is no rebase; the contract is re-evaluated, not replayed.
   This is what lets `mde go` detect that a previously-built plan no longer matches the current rules (e.g. after `init-app` upgrades the method): the method portion of the fingerprint changes, the plan is treated as stale, and `go` rebuilds rather than resuming. Record the method marker in `status.md`/`log.md` so the rebuild reason is visible.

   **A modification made *outside* an evaluation run reverts the plan to `draft`.** Once a plan is `evaluated`, an **external** change to a plan input — the *user* edits a manifest-listed artifact, `scope.md`, or `discussion.md`, an annotation arrives, the method is upgraded — invalidates that evaluation: set lifecycle back to **`draft`** so it must be re-evaluated before `go`. This is the forcing function for changes that happen *between* evaluations.

   **Evaluate's own re-derivation does NOT re-invalidate the plan.** Regenerating the candidate artifacts, impact, and manifest is *part of this evaluation run* (steps 3a–3b) — it is the evaluation settling, not a new external change. Do **not** treat the artifacts you just (re)generated as a "modification" that reverts to draft and demands another evaluate. That is a loop: evaluate regenerates an artifact → counts it as a change → drops to draft → asks to re-evaluate, forever. The correct sequence within one run is: absorb external changes (step 1a) → plan then re-derive everything including the candidate artifacts (steps 3a–3b) → stamp the fingerprint over the **final** state → set lifecycle to **`evaluated`**. The run **finishes evaluated**, not back in draft. Only a *subsequent* external edit reopens it.
7. **If policy `autoCommit: on`** (`specs/design/mde-policy.md`), commit the evaluated plan-local files (`impact.md`, `acceptance.md`, `output.manifest`, `tasks.md`, `status.md`, `log.md`) — e.g. `evaluate: <plan-id>`. When `autoCommit: off` (default), leave them uncommitted. The **candidate artifacts evaluate generated are real but not yet committed** — `go` accepts/commits them; evaluate does not commit durable project artifacts.
8. Show the impact and the generated candidate artifacts (the manifest lists them) to the user for review, then **stop**. **State the result of the final scope self-audit (4c) explicitly** — confirm that the entire scope is complete and tested, or name precisely what is incomplete/deferred and why (never imply "done" when it is not). **Render the go/no-go readout: run `node .mde/method/scripts/plan-ready.mjs <project-root> <plan-dir>` and show its canonical verdict + table verbatim** (GO · GO-WITH-NOTES · NO-GO), then **verify it** per the `mde ready?` profile — independently re-read the evidence and state `Verify: confirmed` or `Verify: disputed — <row>: <why>`. This one readout replaces piecing the verdict together from the raw logs, and gives the user a single, canonical basis for the `mde go` decision (Trust: the script's roll-up; Verify: your skeptical second read). **Then write the plain-English `## Outcome` section into the plan's `status.md`** (per the status template) — Result / What happened / What's wrong / How to fix / How to proceed — so the user reads the outcome and next step in **one file** (`status.md`), never having to dig through `verify.log` / `evidence.md` / `audit.md`. Keep it to those five short lines, derived from the readout above. You **may state that the next step is `mde go`** (informing the user where they are in the lifecycle). You **must not ask the user to commit** — do not solicit the commit, do not pester "shall I commit now? / ready to finalize?", and never prompt for a commit **mid-plan/half-way** through the work. `go` is **user-initiated**: the agent's job ends at a reviewable `evaluated` plan; the user invokes `mde go` (or `cancel`/`change`) when they decide. Report what was produced, note that `go` is next when ready, and wait.

## Validation repair gate

Validation is a repair gate, not a passive report. During step 3c, every finding from
6.1-6.4 must be classified and acted on before the plan can be called evaluated:

- inside confirmed scope and safely fixable: repair immediately, then re-run the affected
  validation pass;
- outside scope: record as a follow-up candidate, not as fixed;
- genuinely environment-blocked executable check: record explicit `verification-debt`;
- requires user intent: open or update `discussion.md` and keep `pending-actions` open;
- required in-scope work still incomplete: set lifecycle to `partially-executed` or
  `blocked`, not `evaluated`.

**`partially-executed` is a stop, not a hand-off.** Classifying findings as unresolved
(stage 9) records *why* the plan stopped; it never converts unfixed in-scope findings
into acceptable completed work. A plan left `partially-executed`/`blocked` because the
verifier failed is **not** a base for the next plan: the next `mde start` on top of it
inherits a known-broken state. If the findings are in scope and fixable, **fix them in
this plan** — repeat repair + re-run (stage 8) until the verifier exits 0. Reach for
classification only when the finding is genuinely out of scope, environment-blocked, or
needs user intent. Cost is not a reason: "the repair is large" makes it a scope or
follow-up conversation with the user, not a silent `partially-executed`.

Only the final clean validation pass may be ticked in `tasks.md`. `evidence.md` must
reference the final validation run after repairs, not only the first failing review.
If 6.4 finds a repeatable bug class that could become a deterministic script, target
check, or template rule, record it as a follow-up validator candidate unless the current
plan explicitly includes method changes. If method changes are in scope, add or update
the validator inside the plan, manifest it, run it, and capture evidence.

## Boundaries

Evaluate **generates** the plan's candidate artifacts at their real project paths (Specs,
source, migrations, diagrams, live pages — whatever the loaded targets mandate) and runs the
full cycle to verify them (steps 3a–3b). What it does **not** do is **commit** them or update the
consolidated root `manifest/` — those are `go`'s job. Evaluate also writes the plan-local working
records (`impact.md`, `acceptance.md`, `output.manifest`, `tasks.md`, `status.md`, `log.md`). So
the generated durable files are **real but uncommitted** until `go` accepts them; cancel/change
roll back exactly the manifest-listed set.

Any material change to the plan after evaluate reverts it to `draft`; the
fingerprint makes that detectable. Building durable artifacts happens at `mde go`,
not here.
